# Decisions
Format: ID, date, decision, alternatives, consequences, approved by.

**D-01 (2026-10-13) Architecture.** Keep the React/Vite UI. Add a server API and a database. Alternative: Next.js (rejected). Consequence: the ZIP's localStorage logic is replaced by API calls. Approved: project lead, chat.

**D-02 (2026-10-13) Loans.** One active loan per member. Interest is information only, with no formula. Approved: project lead.

**D-03 (2026-10-13) Loan in expenditure.** A loan is counted once, through its linked Loan expense. Approved: project lead.

**D-04 (2026-10-13) Access.** Super Admin plus permission-based staff. Staff see their own records. Approved: project lead.

**D-05 (2026-10-13) Restricted permissions.** Only the Super Admin can grant loan disbursement and pay-off permissions. Approved: project lead.

**D-06 (2026-10-13) Authentication.** Email and password. The first owner password is set by a setup script. No default password in git. Approved: project lead.

**D-07 (2026-10-13) SMS.** Fake provider behind an interface. Save the payment first, then report any SMS failure separately. Approved: project lead.

**D-08 (2026-10-13) Data.** Fictional data only until all go-live gates pass. Approved: project lead.

**D-09 (2026-10-13) Delivery.** Lean mode. Whole files pasted in chat. Node version checked by command. Approved: project lead.

**D-10 (2026-10-13) Expense deletion.** Soft-deleted expenses leave the totals and stay in the audit log. Loan-linked and pay-off expenses cannot be deleted. Approved: project lead.

**D-11 (2026-10-13) Automatic Inactive.** A member becomes Inactive only if they have payment history, every refundable balance is zero, and they have no active loan. Approved: project lead.

**D-12 (2026-10-13) Refundable categories.** Shares, Savings, Special Savings, Special Deposit, Building Funds. All other categories are not refundable. Building Funds is a new category. Approved: project lead.

**D-13 (2026-10-13) Stack.** Proposed by Claude in the Understanding Report. Accepted when the project lead replied "Understood, start".
Server: TypeScript (strict), Express 5, Prisma with SQLite for development, Zod for input checks, Vitest and Supertest for tests, ESLint, `exceljs` for Excel, `argon2` for passwords. UI: React and Vite.
Looked up on 2026-10-13 from the npm registry (latest tag unless noted). Compatibility is not yet tested. Final pins are set at step 1.2.
typescript 7.0.2, express 5.3.0, @types/express 5.0.6, prisma 7.10.0 (the `prev` tag), @prisma/client 7.10.0, zod 4.6.7, vitest 5.0.4, supertest 7.3.1, eslint 10.12.0, tsx 4.23.15, exceljs 4.4.0, argon2 0.45.1, vite 8.3.4, react 19.3.0, react-dom 19.3.0, @vitejs/plugin-react 6.1.2.
Alternative: Fastify. Reason for Express: common and well known.

**D-14 (2026-10-13) Repo layout.** `docs/`, `legacy-prototype/` (frozen copy of the ZIP, reference only), `web/` (UI, grown from the prototype), `server/`. Two `package.json` files, no workspaces.

**D-15 (2026-10-13) Money.** Whole kobo as `BigInt`. No decimals. Input with more than 2 decimal places is rejected. Nothing is divided, so no rounding rule is needed.

**D-16 (2026-10-13) Time.** Store UTC. Business dates and month boundaries use Africa/Lagos.

**D-17 (2026-10-13) Balances.** Derived from append-only transaction lines. No stored balance. No clamping of negatives; an action that would make a balance negative is rejected. Corrections are reversing entries.

**D-18 (2026-10-13) UI language.** The UI stays JSX for now. The server is strict TypeScript. Converting the UI is "could", not planned.

**D-19 (2026-10-13) Server pins (step 1.2).** D-13 left final pins to step 1.2. Chosen: express 5.3.0, typescript 6.0.3, @types/node 22.20.5, @types/express 5.0.6, @types/supertest 7.2.1, supertest 7.3.1, vitest 5.0.4, eslint 10.12.0, typescript-eslint 8.71.2, tsx 4.23.15, all exact. TypeScript 6.0.3 replaces the D-13 candidate 7.0.2, because typescript-eslint 8.71.2 accepts only `typescript <6.1.0` (registry lookup, 2026-10-13). Alternative: TypeScript 7.0.2 without a working linter (rejected). Consequence: revisit when typescript-eslint supports TypeScript 7 (A-16). prisma, @prisma/client, zod, exceljs and argon2 are pinned at the step that first uses them. Approved: chosen by Claude as the conventional option under D-13; project lead may overrule.

**D-20 (2026-10-14) Database access.** Prisma 7.10.0 with the `prisma-client` generator, output `server/src/generated/prisma` (git-ignored, regenerated by `npm run db:generate` in `npm run check`), and the driver adapter `@prisma/adapter-better-sqlite3` 7.10.0. Exact pins; `prisma` is a dev dependency. Alternative: `@prisma/adapter-libsql` (not chosen). Reason: the SQLite example in the Prisma docs uses better-sqlite3. Consequence: native module (A-19); `dotenv` 18.0.7 added for `prisma.config.ts`. Approved: chosen by Claude as the conventional option; project lead may overrule.

**D-21 (2026-10-14) Storage interface.** Logic code uses the `Store` interface in `server/src/store.ts`. Two adapters: `prisma-store.ts` (real) and `memory-store.ts` (tests). Both must pass one shared contract suite (`test/helpers/store-contract.ts`). New tables add their methods to the interface and their cases to the contract. Alternative: tests always use a temporary SQLite file (rejected: slower, and the plan asks for an in-memory adapter). Approved: chosen by Claude as the conventional option; project lead may overrule.

**D-22 (2026-10-14) Email normalising.** Logic code trims and lower-cases every email before any store call. The stores keep exact matching (A-21). Alternative: case-insensitive matching inside the stores (rejected: two adapters would have to agree, and it is one rule in one place here). Consequence: any code that reads or writes an email calls `normalizeEmail` first. Approved: chosen by Claude as the conventional option; project lead may overrule.

**D-23 (2026-10-14) Password hashing.** `argon2` 0.45.1 (exact pin), type argon2id, library default cost settings, passwords 12 to 128 characters (A-22). Alternative: a pure-JS hash (kept as the fallback if the install fails on the owner's machine, A-10). Consequence: a native module, like better-sqlite3 (A-19). Approved: chosen by Claude as the conventional option under D-13; project lead may overrule.

**D-24 (2026-10-14) Owner setup.** The first Super Admin is created by a terminal script, `npm run setup:owner`, using `createOwner` in `src/owner.ts`. It refuses if any Super Admin exists (active or not), refuses piped input, asks for the password twice with no echo, never prints it, and writes one `owner.setup` audit entry with the new owner as actor. Alternative: a one-off route (rejected: an open route is an attack surface). Consequence: staff accounts are created later by the Super Admin through the API. Approved: chosen by Claude as the conventional option under D-06; project lead may overrule.

**D-25 (2026-10-14) Permission table.** One table in `server/src/permissions.ts`: 22 permissions, deny by default. Super Admin holds all; Staff hold only granted names that the table lets Staff hold (`users.manage` never). Granting needs `users.manage`, so only the Super Admin grants, including `loans.disburse` and `payoff.process` (D-05, DR-14). Inactive users hold nothing. Alternative: permissions in a database table (not chosen: the list is short, changes with code, and a test pins it). Consequence: staff accounts will store a list of permission names, checked by `hasPermission` on every request. Approved: chosen by Claude as the conventional option under D-04 and D-05; project lead may overrule.

**D-26 (2026-10-15) Sign-in rules.** `authenticate` in `server/src/auth.ts` returns the same `{ ok: false }` for an unknown email, a wrong password, a bad input and an inactive user. Reason codes go only to the audit log (`detail`). The typed email and the password are never stored. The actor is the user when the email is known, otherwise none. An unknown email still checks a dummy hash. An inactive user is refused after the password check. If the audit write fails, sign-in fails (fail closed). Alternatives: return the reason to the caller (rejected: it lets a caller find out which emails have accounts); store the typed email (rejected: it may hold a mistyped password). Consequence: tokens, lockout and routes come in later steps. Approved: chosen by Claude as the conventional option under D-06; project lead may overrule.

**D-27 (2026-10-15) Session tokens.** `server/src/tokens.ts`, no new dependency (`node:crypto` only). Access token: a custom signed format `v1.<payload>.<signature>` with HMAC-SHA256. The payload holds only user id (`sub`), issue time (`iat`) and expiry (`exp`), in whole seconds. No role or permissions in the token, so a change to a user is seen on the next request (A-27). The signature is checked before the payload is read. Default life 900 seconds, longest 86,400 (A-31). The signing secret comes from the `TOKEN_SECRET` setting, at least 32 bytes (A-32). Refresh token: 32 random bytes as 43 URL-safe characters. Only its SHA-256 hash is stored (A-33). Storage and rotation come in step 2.3c. Alternatives: a JWT library such as `jose` (not chosen: a new dependency to look up and pin, and we need only one issuer and one checker); role and permissions inside the token (not chosen: they go stale until the token expires). Consequence: hand-written signing code needs a careful security review (A-34). Approved: chosen by Claude as the conventional option under D-06; project lead may overrule.

**D-28 (2026-10-15) Refresh-token storage.** Table `RefreshToken` (id, userId, familyId, tokenHash unique, createdAt, expiresAt, usedAt, revokedAt). Only the SHA-256 hash is stored (A-33). Tokens from one sign-in and its rotations share a `familyId`. `consume(id, now)` marks a token used in one atomic step and is true only for an existing, unused, unrevoked, unexpired token (expired at its expiry instant). `revokeFamily` and `revokeAllForUser` set `revokedAt` once. A user's tokens are deleted with the user (cascade). Reuse detection and rotation are logic in step 2.3d, built on these methods. Alternative: one `rotate` method in the store (not chosen: it would hide the reuse rule inside two adapters). Consequence: every `Store` literal must include `refreshTokens`. Approved: chosen by Claude as the conventional option under D-27; project lead may overrule.

**D-29 (2026-10-15) Session logic.** `server/src/sessions.ts`: `issueSession`, `refreshSession`, `signOut`. Refresh token life is 7 days, counted from each rotation, with no lifetime cap (A-38). A used token that comes back revokes its whole family and writes `session.reuse_detected` (actor = the user). Unknown, badly shaped, revoked and expired tokens fail quietly. An inactive or missing user has all tokens revoked. A lost race fails without revoking (A-40). Sign-out revokes the family and writes `session.logout`. Correction to D-27: storage is step 2.3c and rotation is step 2.3d (as D-28 says). Alternatives: revoke on a lost race (rejected: the winner's new token may be created after the revoke and survive); a grace window for retries (not chosen: more rules, and no owner request). Consequence: a client that retries a used token must sign in again. Approved: chosen by Claude as the conventional option under D-27 and D-28; project lead may overrule.
